# 内联 UI 块抽取与组件化基线

全仓盘点（#189）发现巨型页面里散落大量组件级内联 UI（同一星形 SVG path 复制 11 处 / 6 文件、空态块 4 处、FamilyAdmin 四段同构骨架、Quiz 选项与反馈条三态、提议卡 504 行等）。经 grilling 拍板（纪要见 #189 评论区），确立组件化新基线并逐块判定抽取归宿；落地走新伞票，前置 prototype 验货。

## 决策

### 组件化新基线（本 ADR 核心）

抽取判定从「复用才抽」改为**「尽量抽」**。动因：单人项目抽象的协调成本为零，而收益实在——

- registry + showcase 可视化浏览全部状态，设计与验收有实体参照
- 组件独立开票、独立上线，变更不碰业务逻辑
- 开发与产品编排为同一人，无跨方协调代价

**红线（贯穿所有抽取）**：受控组件模式——组件只管「按状态渲染」，判定逻辑（哪个选项 correct、哪条反馈是什么 tone、哪行锁定）一律留页面，组件按 props 接收状态。先例：#182 StarCheckCircle（不自带点击切换逻辑）。

### 抽取清单（九件，归新伞票）

| 组件 | 形态要点 |
|---|---|
| StarGlyph | 星形 SVG glyph，`size: 'sm' \| 'md' \| 'lg'`（18/24/48px，默认 md）；fill 恒 `var(--color-star)`，不加 tone（全仓星星单色）；星光雨等多 glyph 动画装饰留页面，glyph 本体归组件 |
| StarEmptyState | 空态块。`icon?: boolean`（默认 true，内部调 StarGlyph lg）；default slot 承文案（覆盖带图标与纯文案两态）；容器不挂 star-container（空态是页面级区块不是卡） |
| StarProgressBar | 进度条。props `value` / `max`；`label?: string` + default slot 双通道（简单文案一句话、复杂内容走 slot）；`position: sticky; top: 0` 吸顶封装进组件（吸顶是进度条本质属性）；Quiz 现役实现为基准，视觉令牌直译 |
| StarSectionShell | 分区卡壳。标题 prop（不用 slot，样式固定组件内）、标题-内容间距固定；错误行+刷新钮、空态两状态组件化（emit `refresh`，错误文案/空态文案由调用方传）；内容 slot 承载列表等业务体。FamilyAdmin 四段为首批调用方；「家庭码」段无错误/刷新/列表、不同构，细节子票内处理 |
| CampAvatar | Proposals.vue 内联 defineComponent（孩子/家长头像两态）升入 `src/components/` 并注册；实现已有，搬家+注册+showcase |
| StarRewardItem | 奖品行（锁态 chip + 星形价签 + 兑换钮）。props：名称/价格/锁态（余额不足）；emit 兑换。Redeem 现役实现为基准 |
| StarOptionRow | 答题选项块。props：文案 + `state: 'normal' \| 'correct' \| 'wrong' \| 'reveal'`；emit 选择。判分逻辑（optionClass）留页面 |
| StarFeedbackBar | 答题反馈条。props：`tone: 'correct' \| 'wrong' \| 'skipped'` + 文案；icon 由 tone 决定 |
| 提议卡拆件 | Proposals 卡（504 行大头）拆卡壳+双阵营区+操作行成组件。工程量最大，独立子票标注 |

### 不抽决策

- **bottom-action-bar**：保 CSS 约定。结构太薄（`<footer>` 包一个 StarButtonStandard，两行 HTML），样式已全局（components.css），组件化只添间接。#184 StarBatchBar 是批量专用壳（count/feedback/clear），不同量级，不动。
- **CardToggle / SuperPowerCard**：名义公共实为 Parent 私有——现状即正确（Parent 私有 by design），不进 registry、不改文件位置。
- **星光雨**（Result）：页面私有 CSS 动画装饰，非 glyph 本体。

### 落地路径与归属

- **新伞票「散落组件整理与升级」**承载九件，与 #188（家长端批量改题组件齐套，#163 收口）并列；#188 语义保持纯净不受影响。
- StarProgressBar 归新伞票而非 #188：其抽取动机是 Quiz 页散落进度条的整理（#163 原型里的批量条已由 #184 StarBatchBar 覆盖，进度条非那批缺口）；票内注明批量改题生产页落地后将复用。
- **prototype 验货关口前置**：九件先在单文件 HTML probe 中呈现全部形态/props/状态矩阵（probe-1/probe-2 同款工作流，scratch 会议室产物不入库），老板逐件拍板定稿后，九张子票（C- 前缀 + #182–#187 Brief 骨架）以 probe 为准另开。
- 单篇 ADR 承载全部判定；后续形态调整走修订记录。

## Considered Options

- **复用才抽（旧基线）**（否决）：单消费方块被长期留在页面里自生自灭，showcase 不可见、变更耦合业务页；单人项目下协调成本论据不成立。
- **多 ADR（每组件一篇）**（否决）：九件判定是同一组权衡的产物，拆篇互相引用、啰嗦；0005 先例即一篇记一组相关决策。
- **九票直接开、无 prototype**（否决）：props/状态矩阵仅文字 Brief，老板无法在开票前放心视觉形态；插 prototype 关口（#163 先例：先验货后开票）。
- **Section 卡壳等第二消费方再抽 / 保持页面内联**（否决）：四段同构强信号 + 新基线下「尽量抽」；错误/刷新逻辑留页面、结构收编的 slots 方案解耦干净。

## Consequences

- 组件库从 7 件增至 16 件（九件 + 既有），registry 与展示页相应扩容；每件子票验收含 showcase 四态/全态呈现与 vitest。
- 页面显著减负：FamilyAdmin（526 行）、Proposals（504 行）、Quiz、Redeem 的内联块各归组件。
- 判定逻辑留页面的受控模式是硬约束：子票 Brief 里 props 契约以「状态传入」为准，组件源码不得出现业务判定。
- StarGlyph 落地后 11 处 path 复制清零；后续新增星星场景一律调组件，不得再复制 path。
- #188 与新伞票互不阻塞，可并行推进；合并仍须串行（多机协作口径）。
- 子票开工顺序：prototype 定稿 → 便宜的先走（StarGlyph / StarEmptyState / CampAvatar）→ 提议卡拆件收尾（工程量最大）。
