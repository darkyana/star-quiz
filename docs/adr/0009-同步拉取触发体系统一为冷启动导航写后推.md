# 同步拉取触发体系统一为冷启动+导航+写后推

## 背景

本地优先架构下（ADR 0002），云端拉取此前只有三个触发时机：冷启动（组合根 `startSync`，#126 收口）、本地写入后连带同步、配对成功后一次。拉取落库后无页面通知机制——多设备场景下 A 设备的更新要等 B 设备下一次冷启动才可见，表现为「一端更新后另一端很长时间收不到新信息」（典型：首页星星数量不实时）。

服务端推送通道（WebSocket/SSE/Web Push）与定时轮询被明确排除（#208 Out of scope）：纯客户端拉架构下，导航时机是天然存在的最高频「该看看有没有新数据」时刻。

## 决策（#208，2026-09-08 落地）

拉取触发体系统一为**「冷启动 + 导航驱动 + 写后推」一套**，不另设冷启动专用通道：

1. **导航触发收口唯一**：路由全局守卫一处调 `onNavigationSync()`（`src/router/index.ts`），不散落各页面；延续「触发点收在组合根/全局收口」的架构约定（#126）。
2. **进行中去重**：`cycleInFlight` 标志保证同一时刻只跑一轮同步周期；进行中再触发改排一轮 trailing 补跑，不并发、不丢失。
3. **短节流 + trailing 补跑**：`NAVIGATION_PULL_THROTTLE_MS = 5000`（票面 5–10s 取下限——多端滞后是本票痛点，宁可多拉）；窗口内快速切页只打一轮，窗口结束补跑一轮保证最后一次导航的数据不丢；即时轮触发时取消既定补跑防近距双轮。
4. **拉取完成广播**：`registerSyncCompleteListener`（对齐 `registerWriteListener` 的 Set + 注销函数风格）；广播时机 = 同步周期有远端行**实际落库**（`SyncPullResult.landed`），成功但零新行不广播；四条拉取通道（bootstrap/增量拉合/损坏对账/断代重对齐）统一回报 `landed`。
5. **页面静默刷新**：页面只订阅 + 重读本地（先例：首页星星余额），守卫不等待拉取、失败静默（`getLastSyncOutcome` 仅内部备用字段，无失败 UI）。

既有 gating 原样保留且判定单一出口不变：未配对零网络（#125）、测试模式零推零拉、协议不兼容空转（#174）——导航触发空转同样走 `runCycle` 内判定。

## 理由（ADR 三条件自检）

- **难逆转**：触发体系与广播 API 是页面数据新鲜度的地基，页面订阅散开后回收成本高。
- **事后会问**：为什么切页会发同步请求？为什么有时切页不发？——节流/去重/落库判定若无常设记录，事后难追溯。
- **真实权衡**：请求频率（5s 窗口上限约 2 轮）vs 数据新鲜度；静默失败 vs 失败提示 UI（后者留给 #209 及后续票）。

## 后果与范围

- 多端同步滞后修复：进入页面即静默对齐云端最新，停留页面落库后无感更新。
- 页面接入按最小必要渐进（首批仅首页），其余页面依赖「导航重挂载 + 导航触发拉取」链路，可逐页接订阅。
- 不做：服务端推送、定时轮询、手动刷新、失败提示 UI、存储层改动。
