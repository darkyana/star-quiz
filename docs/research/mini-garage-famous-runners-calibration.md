# 迷你车库：知名原作速度与障碍节奏校准依据

> 调研日期：2026-09-14 UTC。只新增本文件，不修改游戏。沿用 `mini-garage-speed-primary-sources.md` 的来源门槛，但补足知名原作、归一化尺度及可复算动作周期。所有数值区分「源码事实」「本文推导」「待实测」；本次没有测量任何游戏录像，也没有完成原版游戏的浏览器实玩测时。

## 结论先行

1. **有两个可量化的知名原作实现**：Chromium Dino 固定版本，以及微软官网实际分发的 **Surf Lite Edition v7**。后者是官方原作的精简版，不是第三方复刻，也**不能代表当前完整版 `edge://surf`**。
2. **商业跑酷调查没有取得可用的基本速度／预警／障碍间隔参数**：实际访问了 Subway Surfers 官方帮助页、Temple Run 官方 FAQ；Crossy Road 支持页访问成功但正文提取不完整。Subway 的「滑板保护30秒」可量化，但不是速度或障碍节奏，不能拿来充数。
3. Dino 在600逻辑像素宽度下，名义速度 **0.60→1.30屏宽/秒**；保守几何前视约 **1.411→0.651秒**。Surf Lite 的正常直行目标速度 **450画布像素/秒**，必须除以实测画布高度 H 才能得到 **450/H 屏高/秒**，不能硬说它固定为某个屏/秒。
4. **这些证据既不支持直接照搬 `6`、`7.5`，也不支持直接宣称本地 `25→40` 合理。** 先把本地速度换算为有效前视秒、完成躲避所需时间和障碍危险事件间隔，再比较。知名游戏不是儿童反应时间标准。

## 2. 统一量纲：不要把不同坐标里的速度裸值比较

以下为运动学定义，不是某款游戏的官方调参建议。

- **屏幕轴归一化速度**：二维匀速投影下 `r_x=|v_x|/W`（屏宽/秒），`r_y=|v_y|/H`（屏高/秒）。Dino 横向滚动，Surf 向下滑行，应各用其运动轴；强行都除屏宽会受到纵横比干扰。
- **几何前视**：`T_geo=D_geo/v_rel`，从边缘出现到首次可能接触碰撞边界；不是认知预警。
- **有效前视**：`T_eff=t_collision−t_recognizable`，后者是障碍形态／所需动作真正可辨认的时刻。细小、遮挡、透明图案和透视都会缩短它。源码边缘位置无法单独证明这个时刻。
- **动作周期**：输入生效至恢复下一动作资格的耗时。连续转向没有天然「一跳周期」，应报告完成给定侧移距离的耗时 `A(d)=d/|v_x|`；需另加输入延迟、状态限制。
- **障碍节奏**：分开记录净空时间、同类障碍前缘到前缘间隔、生成批次间隔，以及真正要求动作的事件间隔。它们不能互换。
- 可跨机制比较的是 `T_eff/A` 和 `事件间隔/A` 的数量级，但跳跃可能一次跨多个障碍、连续转向又可能同时推进，二者仍不是完全等价任务。三维透视游戏应记录时间或世界单位／秒，而不是以远近变化的像素流速代替前進速度。

## 3. Chrome Dino：可复算的速度、前视、跳跃与 gap

### 3.1 默认桌面场景的名义速度

[D] `Runner.config`、`Runner.defaultDimensions`：`FPS=60`、宽600、高150、`SPEED=6`、`MAX_SPEED=13`；`Obstacle.update`（L1476–1481）实际做 `x -= floor(speed*60/1000*deltaTime)`。

| 指标 | 初始速度参数6 | 目标上限参数13 |
|---|---:|---:|
| 名义速度 `60s` | 360逻辑px/s | 780逻辑px/s |
| `60s/600` | 0.600屏宽/s | 1.300屏宽/s |
| 全画布横穿时间 `600/(60s)` | 1.667s | 0.769s |
| 保守外框前视 `508/(60s)` | 1.411s | 0.651s |

**508如何得到**：开场结束恐龙 `x=50`、宽44；外层碰撞框左51、宽42，右缘93。障碍外框左缘为 `obstacle.x+1`，故它向左到 `x<92` 时才可能外框相交。从障碍左缘刚到视野右边600起算，距离 `600−92=508`。细分碰撞盒还有第二道检查，因此这是偏保守的几何边界，不是实测首碰时间，也不是保证玩家已经看清。依据：`Trex.config` L1640–1653，`checkForCollision` L1219–1265。[D]

边界：

- 上表为恒速名义换算。逐帧 `floor` 会损失不足1px/次更新；低于上限时每次更新加0.001，而非每秒加0.001，因此实际位移和加速依赖帧节奏。不能把上表当任意设备实测值。[D L538–578]
- 60次更新/秒时，名义加速为参数0.06/s，即3.6逻辑px/s²；参数6到13约116.7秒更新时间。开场动画、暂停、掉帧会影响墙钟时间；最后一次递增可能略超上限。[D]
- 窄屏 `setSpeed` 使用 `min(s,s*W/600*1.2)`，并非始终保持统一屏宽/秒；后续加速仍走上述累加逻辑。设备像素比不等于逻辑游戏宽度。[D L340–350]
- `CLEAR_TIME=3000ms` 只是障碍启用门槛。开场动画与障碍从画外移动进来还需时间；不能说「开始后恰好3秒首次碰撞」。翼龙 `minSpeed=8.5` 且相对速度带±0.8，不能套用静止仙人掌的所有算式。[D]

### 3.2 跳跃周期：执行原版运动方法，而不是猜动画秒数

[D] 真正被 `Trex.startJump` 使用的是拼写如此的 `Trex.config.INIITAL_JUMP_VELOCITY=-10`；`Runner.config.INITIAL_JUMP_VELOCITY=12` 不是可直接代入默认跳跃的值。`startJump` 设置速度 `−10−s/10`；`updateJump` 每帧 `round` 位移、加重力0.6，达到最大高度条件会截断上升速度；不能只套 `2v/g`。[D L1640–1653、1728–1732、1868–1922]

在60Hz等步长、地面y=93、无碰撞／快速下坠、固定起跳速度参数条件下，实际执行原版方法得到：

| 输入 | s=6 | s=13 |
|---|---:|---:|
| 一直按住，至自动落地 | 35帧＝0.583s | 34帧＝0.567s |
| 第4次更新后松开 | 28帧＝0.467s | 28帧＝0.467s |

这是**源码隔离执行结果**，不是原版录像／浏览器输入端到端测量；松键时机可改变结果，按下方向键快速下坠另算。落地后下一帧／下一输入事件能否立即重跳也应单独实测。

复现（先从[D]链接的 `?format=TEXT` 下载并Base64解码到 `offline.js`；只读原作，不需要改本地游戏）：

```js
// node；用原文件方法计算，不重写跳跃方程。
const fs = require('fs'), vm = require('vm');
let code = fs.readFileSync('offline.js', 'utf8');
code = code.replace(/\}\)\(\);\s*$/, 'window.Trex=Trex;})();');
const ctx = { window: { devicePixelRatio: 1,
  navigator: { platform: '', userAgent: '' } }, document: {} };
vm.createContext(ctx); vm.runInContext(code, ctx);
const T = ctx.window.Trex;
for (const speed of [6, 13]) for (const releaseFrame of [null, 4]) {
  const t = Object.create(T.prototype);
  Object.assign(t, { config: T.config, groundYPos: 93, yPos: 93,
    minJumpHeight: 63, jumping: false, jumpCount: 0,
    update(dt, status) { this.status = status; },
    reset() { this.jumping = false; } });
  t.startJump(speed);
  let n = 0;
  while (t.jumping && n < 100) {
    n++; t.updateJump(1000 / 60);
    if (n === releaseFrame) t.endJump();
  }
  console.log(speed, releaseFrame, n, n / 60);
}
```

### 3.3 障碍间隔：gap不等于动作周期

单个小仙人掌 `w=17`、`type.minGap=120`，`gapCoefficient=.6`、`MAX_GAP_COEFFICIENT=1.5`；`g_min=round(w*s+120*.6)`，`g_max=round(1.5*g_min)`，整数随机。[D L1508–1512、1546–1559]

| 单个小仙人掌示例 | s=6 | s=13 |
|---|---:|---:|
| 随机gap参数 | 174–261px | 293–440px |
| `gap/v`（仅参数对应时间） | 0.483–0.725s | 0.376–0.564s |
| 连续两只单个小仙人掌前缘周期，连续近似 | 0.578–0.819s | 0.419–0.608s |

最后一行不是 `(g+17)/v`：上一障碍右缘加gap进入画布才触发下一只，下一只又从 `W+下一类型宽度` 出生。因此同类单只示例的前缘距离为 `g+17+17`，还需计入严格 `<` 条件造成的至多一个更新步长触发偏移（等速60Hz时至多约16.7ms）。依据：构造器L1357–1367、`updateObstacles` L2866–2878、`addNewObstacle` L2890–2904。[D]

边界：小仙人掌可有1–3个分组，宽度会变；不同类型、分组和翼龙的间距不等于上表。一次跳跃可能越过一组或多只，所以不能从前缘周期小于跳跃周期断言无解，也不能把随机gap当作三车道连续有解证明。

## 4. 第二个可信原作：Microsoft Surf Lite v7

### 4.1 速度与屏幕归一化

[S1] `resetCurrentPlayerData`：`speed:{current:0,x:0,y:0,initial:1,raw:0,max:7.5,base:7.5,accel:.02,airAdd:2.5,boostAdd:5}`；核心 `update(e)` 把毫秒转成 `time.loop=e/1e3`、`time.scale=60*time.loop`；`updateSpeed` 用raw乘scale作为当次位移量。

恒定帧节奏的名义推导：

- 开始移动：`1*60=60px/s`；普通目标：`7.5*60=450px/s`。
- 普通加速：`.02*60*60=72px/s²`，raw1到7.5约5.42s，忽略第一帧与离散越界／浮点振荡。
- 腾空目标600px/s、boost目标750px/s是其他状态，不应混入普通速度。STOP可令速度为0，因此它不是永远不能停止的强制前进跑酷。[S1 `updateSpeed`、方向处理]
- `defineCanvas` 从父元素CSS宽高读出W、H，画布使用相同数值；玩家锚点 `x=floor(.5W), y=floor(.4H)`。正常直行向下时 **屏高速度=450/H**，粗略「底边到玩家锚点」前视 **`[H−floor(.4H)]/450`秒**。[S1]

**不能补造实测画布尺寸**：本次没有运行并记录viewport，因此报告保留H。举例仅为算术校验：若未来实测H=600，则目标0.75屏高/s、粗略锚点前视0.8s；这个600不是本次官网实测值，也不是官方默认值。

粗略锚点前视还不是 `T_eff`：玩家与障碍有各自碰撞盒；图像透明边界、侧向接近、前景遮挡和不同物体尺寸都会改变首次可辨认及碰撞时刻。不能把它拿来直接比较Dino更保守的外框前视而不注明定义差异。

### 4.2 连续转向，不存在通用固定「换道动画秒数」

[S1] 普通直行速度450时，较浅斜向（相对直下±30°）为：侧向225px/s、前向389.71px/s；较陡方向（±48°）为：侧向334.41px/s、前向301.11px/s。因此侧移d像素的名义时间分别为 `d/225` 或 `d/334.41`，同时还在向前移动。

方向输入在状态层直接改变方向，但受air/crash/bounce等守卫限制；不能因此宣称设备输入延迟为0。`doubleDelta=300` 是双按DOWN触发boost的**毫秒输入窗口**，不是换向完成时间。Boost默认持续2400px距离，不是恒定秒数。[S1]

### 4.3 障碍簇生成批次，不是单障碍或动作间隔

[S1] `grid:{size:32,gap:16,height:12,padding:12}`：

- `xGap=(16+12)*32=896px`，`yGap=(12+12)*32=768px`。
- `row.next` 初始64；当 `row.next < distance.yPx`，执行 `createGameClusters()`，随后增加 `yGap+padding*size*2=1536px`。
- 正常450px/s直行稳定阶段：每1536px约 **3.413s一次生成批次**；首批条件为纵向距离超过64px。
- 每批包含5个簇位置，x偏移 `[0,+896,−896,+448,−448]`、y偏移 `[0,0,0,+768,+768]`，另有具体图案和随机物件。**绝不应写成「每3.41秒一个障碍」或「玩家有3.41秒反应」**。

该实现的可靠对照意义是：速度可以用时间因子转换，布局／批次沿行进距离安排，动作又能改变前向与侧向速度；不是可直接搬到三车道的固定生成秒数。核心更新与物体更新存在次序差异，变帧率下不宣称精确积分；上述450与3.413为稳定节奏名义推导，不是实玩测量。[S1]

## 6. 对本地重新校准的可执行建议（非本次改动）

先建立下面这张本地测量表，再决定25、40或其他值；本文件不声称已经测过本地场景。

1. **锁定版本／场景／设备**：提交号、画布W/H、逻辑和世界坐标、实际帧率、触屏／键盘、普通／加速状态。
2. **记录可辨认到危险边界的距离或时间**：对最小和最大障碍分别测 `T_eff`，不能把整个跑道绘制深度当有效前视；3D透视优先逐帧计时。
3. **测动作耗时**：单道和跨两道的碰撞体脱险耗时、连续输入间隔、缓动／冷却；取 `B=辨认决策+输入+动作+安全余量`，确保 `T_eff≥B`。这里只定义预算，不把儿童反应时间凭空设为某个值。
4. **固定时间目标后反推速度**：恒速 `v=D_eff/T_target`；变速解 `∫v(t)dt=D_eff`。如果同一场景、有效距离不变，25→40会让前视时间乘 **0.625**，即缩短37.5%；这是比“只快15”更有意义的变化描述，不是支持这次提速的结论。
5. **联动障碍间距与连续可达性**：净空距离至少 `v_rel*所需动作预算`，同时校验未来多排的车道—时间路径。不能用Surf批次3.413秒或Dino随机gap直接充当保证。
6. **比较而不照抄**：Dino的几何前视约0.65–1.41秒、跳跃约0.47–0.58秒可作为高密度单动作参照；Surf采用连续方向控制，比较其 `A(d)` 与前视比例。儿童／新手可选择更宽时间预算，但具体档位仍需目标用户试玩，不是从名作知名度推出。

### 若必须拿到商业原作定量值

可信下一步是向作者索取版本化说明，或真正测量官方原版演示：记录官方发布者、链接、发布日期／构建号、原始帧率、未剪辑区间；逐个标注障碍首次可辨认帧、到达碰撞线帧、动作起止帧，报告 `(终帧−始帧)/fps` 和至少±1帧标注误差。不能跨剪辑点计算，不把宣传片镜头当实机，不把倍速视频当实时。无已知世界距离时只报时间和归一化屏幕位移，不杜撰m/s。此为后续协议，本次没有完成这些测量。
