多一个 module，就更好吗？

第一课 · 约 6 分钟 · 不需要读代码 · 架构判断速查表

AI 说：“这里有点复杂，我建议再拆一个 module。”你不必立刻赞成或反对。今天只学会追问一句：拆完以后，谁少操心了什么？

先看你自己的 App

家长和孩子商量好一个兑换项后，家长按“发布兑换项”。屏幕上的一个动作，内部有几方合作。下面是当前代码的简化调用图，不是改造建议，也不是完整 App 架构。

  1. 提议板页面：接住点击
    告诉发布功能“发布这条提议”；调用结束后重新读取列表。
  2. 发布功能：组织这件事
    找到提议，询问发布门禁；通过校验后，追加兑换项，再保存提议的“已发布”状态。
  3. 状态规则：回答能不能发布
    检查是否已经结束，以及家长、孩子是否都同意。它负责判断，不负责画按钮，也不负责保存。

读图提示：发布功能会先询问状态规则，得到答案后才继续写入。图中是职责和调用关系，不是“第一步存好，第二步再检查”。发布按钮显示时也会使用同一套门槛判断；真正执行发布时还会重新检查。

Module 不是“一个文件夹”

Module 是一块有对外约定、也有内部做法的代码。今天我们缩小镜头，把“发布功能”当作一个 module 观察；它只是所在文件的一部分。

  • Interface（对外约定）：正常调用时告诉它提议编号；它尝试发布，返回成功或拒绝原因。调用者仍要理解“发布会新增兑换项，并结束该提议”。
  • Implementation（内部做法）：去哪找提议、怎样询问规则、怎样追加兑换项、怎样保存状态。

这里的 interface 不是屏幕界面。调用者就是“使用这块代码的其他代码”，本例中是提议板页面。好处不在于页面少写几行，而在于页面不必自己安排整套发布手续。

对比两种方案

以下是教学假设，不是说 repo 目前存在方案甲。

甲：页面亲自办手续

页面自己判断双方同意、排除已作废和已发布、追加兑换项、更新提议。将来别的入口也能发布时，又得正确安排同一套手续。

乙：页面委托发布功能

页面提交提议编号，由发布功能安排手续。其他入口使用同一能力，不必抄一套。现有代码在这件事上采用了这个方向。

乙的价值是把需要一起知道的细节集中起来。这与 Parnas 的信息隐藏原则一致：划分 module 应考虑隐藏什么设计决策，而不是把每个执行步骤都拆成一个。

这也给“深 module”一个直觉：使用者学会少量约定，就能办成一件有分量的事。不是把代码写长，也不是把不相干的能力全放进去。本课只看这一处收益，不给整个文件评“深浅分”。
